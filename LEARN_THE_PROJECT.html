1. The idea in plain English

Every connection goes through a middleman (a proxy). The proxy checks an ordered list of rules. The first rule that matches wins. A web dashboard lets an admin edit the rules and approve people's requests for temporary access, which expires by itself.
Analogy: the school security desk.
Students don't walk straight into other buildings. They go via a desk. The guard has a clipboard of rules, top to bottom: "Bob may enter the Lab until 3pm" / "Nobody enters the Lab". The guard reads from the top and obeys the first line that applies. If Bob asks for access, the principal (admin) writes a new line at the top with an expiry time. When 3pm passes the line stops applying, and the old "Nobody enters" line takes over again. The guard never needs to be told to remove it.

What problem does it solve?

  • Block unwanted sites (e.g. YouTube) for some or all users, in one central place the user can't switch off from the browser.
  • Let people ask for a short exception, with a reason, and let an admin approve it, without editing config files.
  • Inspect and filter content (keywords, card numbers, executable downloads) in a lab environment.
  • Keep an audit log of who tried to reach what.

The two things you will say most often

"First match wins."
Rules are checked top to bottom. Order is the logic. That's why a temporary allow is inserted at position 0.
"Expiry is enforced in the data path."
The proxy itself compares expires_at with the clock on every request, so even if the dashboard crashed, access would still end on time.

2. Vocabulary you need

Proxy / forward proxy
A server that makes requests on behalf of a client. In a forward proxy the client is configured to use it (this project). A reverse proxy sits in front of servers instead (load balancers, CDNs).
ACL (access control list) / rule
An ordered list of allow/deny conditions. Here: who (user), what (domain, service, path, method), when (schedule), from where (IP range).
Default action
What happens if no rule matches. Default deny = whitelist (safer). Default allow = blacklist (practical for browsing).
HTTP CONNECT
How a browser asks a proxy for an HTTPS tunnel: CONNECT youtube.com:443. The proxy then just copies encrypted bytes back and forth. It can only see the hostname, not the page or content.
TLS / HTTPS
Encryption between browser and website.
Mutual TLS (mTLS)
Both sides show certificates. The client certificate's Common Name (e.g. bob) becomes the user's identity, which can't be faked by editing a header.
CA (certificate authority)
The thing that signs certificates so others trust them. gen_certs.py makes a project CA.
TLS interception
The proxy pretends to be the website using its own CA-signed certificate. Needed here only to show a block page for HTTPS sites.
Immutable object
Never modified after creation. Policy changes build a new Policy and swap it in, so threads never see half-edited rules.
CSRF
A malicious site tricks your logged-in browser into submitting a form to the dashboard. Defence: a secret token in every form.
SSRF
Tricking a server into fetching internal addresses (localhost, LAN). Relevant to the Browse page.
Service worker
A script a site installs in your browser that can serve cached pages offline. It's why a blocked YouTube first looked "offline".

4. The story: one complete user journey

This is the heart of your demo. Learn it as a story with four acts.

Act 1: Blocked
  1. Admin adds a rule on the Website access page: deny * → youtube.com.
  2. Bob opens youtube.com. The browser sends CONNECT youtube.com:443 to the proxy on :8080.
  3. The proxy checks Bob's proxy password (407 if wrong), then runs match_rule("youtube.com","bob"). The deny rule matches → verdict: deny. It logs the event and never opens a connection to YouTube.
  4. With --block-page Bob sees a real page: why it is blocked, by whom, and a Request temporary access button.
Act 2: Request
  1. Bob signs into the dashboard and submits: site = youtube.com, 5 minutes, a reason.
  2. The app only accepts sites the proxy currently blocks for Bob (it uses the same match_rule function, so the two can't disagree). Nothing changes yet. The request is pending.
Act 3: Approve
  1. Admin opens Access requests and clicks Approve. Only admins can; it's enforced on the server (@role_required("admin")), not just by hiding a button.
  2. A rule is inserted at index 0: 
    {"action":"allow","users":["bob"],"domains":["youtube.com"],
 "temporary":true,"expires_at": now + 5*60, "grant_reason":"…"}
  3. Bob reloads: first match is now this allow → the proxy opens a tunnel. Carol is still blocked, because the rule names only Bob.
Act 4: Expire or revoke
  1. Five minutes pass. rule_expired() returns true, the proxy skips that rule, and the older deny matches again. No cleanup job is needed for correctness.
  2. Already-open tunnels are not forgotten: every second tunnel() re-runs match_rule and stops at the deadline. An admin Revoke cuts a live YouTube stream within about a second.
  3. purge_expired_real_rules() later tidies dead rules out of the JSON file (cosmetic only).
Design decision to defend: where is expiry enforced? In the proxy's data path, not just in a background job. Failure of the dashboard can't leave a site open.

An animated version of this journey is in packet_flow.html (same folder). Open it in a browser during your rehearsal.

5. Rule engine: try it yourself

This simulator mirrors match_rule() from forward_proxy.py. Change the user, the site and whether the temporary grant is still valid, then watch which rule wins.

Things to notice

  • www.youtube.com and googlevideo.com are covered by the youtube.com rule (subdomain match plus the DOMAIN_FAMILIES table).
  • notyoutube.com is not blocked. The match is host == d or host.endswith("." + d), so a look-alike suffix doesn't trick it. There's a test for this.
  • Default action is allow in Layer B. In Layer A it is deny.

The actual code (it's short)

def match_rule(host, user):
    host = host.lower().rstrip(".")
    policy = read_policy()
    for rule in policy.get("rules", []):
        if not rule.get("enabled", True) or rule_expired(rule): continue
        users = rule.get("users", ["*"])
        if users and "*" not in users and user not in users: continue
        if domain_hit(host, rule):
            return rule.get("action", "deny"), rule      # FIRST MATCH WINS
    return policy.get("default_action", "allow"), None

Layer A's richer rules

Layer A rules can also match user groups (@staff), source network, service, path (/admin/*), HTTP method and a time schedule. The shipped sample policy:

IDEffect
R01Staff allow
R02Quarantined network deny
R03Anonymous users can't use chat/files
R04Deny /admin on web
R05Deny /social Mon–Fri 09:00–17:00
R06Students allow
R07Guests: web + echo only

Two-stage evaluation: at connect time the proxy knows user, IP, service and time. At request time it also knows method and path. A path rule can't be decided at connect time, so a deny is deferred and an allow admits provisionally.

Path normalisation (normalize_path) turns /%61dmin, //admin and /x/../admin into /admin before matching, and the proxy forwards the normalised path, so what was checked is exactly what is served.

Dynamic policy: Policy is immutable. Any change builds version+1 and swaps it atomically. A watcher polls the file each second; invalid files are rejected and the old policy stays. After each swap, revalidate() re-checks every open connection and kills the ones now denied.

ActionEffect

If several match: any block wins outright → then redactions → log filters only record.

The clever part: keywords split across packets

TCP is a stream with no message boundaries. One recv() can return half a line. If you only scan each chunk, "confi" + "dential" slips through. StreamInspector buffers bytes into complete lines and holds back any tail that could be the start of a blocked word. A test (test_every_segmentation_gives_same_result) checks the verdict is identical however the data is chopped.

Why strip Accept-Encoding? A gzip body can't be scanned, so the proxy asks the server for uncompressed responses.

Why a browser can't just show "blocked"


For HTTPS the browser sends CONNECT before TLS. If the proxy refuses, browsers throw away the refusal's body and show their own error. To show a real page, the proxy must answer 200 and do the TLS handshake itself with a certificate from its own CA, which the browser must trust once. This is called TLS interception; it's only done for blocked hosts. Allowed traffic stays end-to-end encrypted.







8. Honest limitations


Presenters who name their own limits sound credible. Say these before someone asks.


    

  1. Hostname-only for HTTPS. It can block youtube.com but not one video on it.
    2. 

  2. Bypassable. Only traffic sent to the proxy is filtered. A VPN, DNS-over-HTTPS or switching the proxy off avoids it. Real enforcement needs a gateway or firewall.
    3. 

  3. Demo-grade authentication. Layer B uses Basic proxy auth (cleartext on the wire) with public demo passwords and a non-constant-time == compare. Fine on loopback only.
    4. 

  4. JSON file as the database. Writes are atomic but two admins editing at once could race.
    5. 

  5. Layer B detects revocation by polling every second; Layer A is pushed the change instantly.
    6. 

  6. Flask development server, not production.
    7. 

  7. Layer A listens on 0.0.0.0 and ships with a default admin token and no mandatory client certificate. Tighten before any shared use.
    8.

10. Likely questions and short answers


What does your project do?
It filters network access through a proxy using ordered rules. A dashboard lets an admin manage rules and approve requests for temporary access, which expires automatically.


Why use a proxy instead of filtering in the browser?
It's central, outside the user's control, works for any app that honours the proxy, and gives one place to log and audit.


Can the proxy see which page I visit on an HTTPS site?
No. Only the hostname from CONNECT. The path and content are inside TLS. Seeing them would need TLS interception.


What does "first match wins" mean and why does order matter?
Rules are tested top to bottom and the first whose conditions all match decides. A temporary allow must sit above the deny to override it, so it's inserted at position 0.


How does a site re-block itself after the time is up?
match_rule skips rules where rule_expired() is true, so the older deny underneath matches again. It's enforced in the data path with no job required.


What about a tunnel already open when time runs out or access is revoked?
tunnel() wakes every second, stops at the grant's deadline, and re-runs match_rule for that host and user, so it closes within about a second.


How do you stop a user approving their own request?
Approve, reject and revoke routes require the admin role, enforced server-side (403 otherwise). Hiding a button isn't security.


What is CSRF and how do you prevent it?
A malicious site makes your logged-in browser submit a form to the dashboard. Each session has a random token every POST must include, checked with hmac.compare_digest.


How are passwords stored?
Salted PBKDF2-SHA256 hashes via Werkzeug. (Scrypt, the default, isn't available in this Python build, so PBKDF2 is set explicitly.)


Why can't you scan each recv() chunk for keywords?
TCP has no message boundaries, so a keyword can be split across chunks. StreamInspector buffers into lines and holds back any possible keyword prefix.


Block, redact and log: what's the difference?
Block refuses or terminates, redact replaces the text and continues, log only records. A block wins over everything.


What is mutual TLS and why use it?
Both sides present certificates. The client certificate's Common Name becomes the identity, which can't be faked by editing a header. No certificate means anonymous.


How do rule changes apply without restarting?
Policy objects are immutable; changes build a new version and swap it atomically under a lock. A watcher polls the file mtime. After each swap, revalidate() kills open connections that are now denied.


Why does a blocked HTTPS site show "can't be reached" instead of a message?
The browser asks for a tunnel before TLS; when refused it discards the body. The block page works by answering 200 and doing TLS with a certificate from a locally trusted CA, only for blocked hosts.


Isn't trusting your own CA dangerous?
Yes, while trusted, whoever has ca.key can mint certificates for any site on that machine. Mitigations: dedicated CA, key locked down and git-ignored, 30-day certificates, strict host validation, only blocked hosts intercepted, trust removed afterwards.


How does the Browse page avoid SSRF?
Only http/https, the host must resolve to a public IP (so localhost and the LAN are refused), redirects are followed manually and re-checked at each hop, the preview is sandboxed with scripts off, and login is required.


What if the user turns off the proxy setting?
Filtering is bypassed. A proxy only filters traffic sent to it. Real enforcement needs network-level controls.


How would you scale it?
Replace JSON with a database or cache, use async I/O or a process pool, central logging, hashed credentials or SSO.


Why simulated services?
A safe, self-contained lab: reproducible demos and tests without touching real sites.
